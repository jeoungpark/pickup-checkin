## 1. 전체 이용 시나리오

step.1 운전자는 운행 전에 `태우러가기` 또는 `데려다주기`를 선택하고, 이번 운행의 대상·방문 순서·장소·보호자 링크를 확인한다. 보호자는 자기 대상의 링크만 받는다.

step.2 운전자가 운행을 시작하면 차량 앱은 내비에 경유지를 요청하고, 중계 서버는 이번 운행에 연결된 보호자에게 출발 상태를 전달한다. 알림 발송 결과는 차량 앱에 표시한다.

step.3 차량이 다음 지점에 접근하면 해당 보호자에게 `곧 도착`을 한 번 알린다. 차량이 지점 인근에서 P 상태가 되면 `도착·대기`로 전환한다. 접근과 도착은 별도 이벤트다.

step.4 P 중 조수석·뒷문 또는 설정된 트렁크의 열림→닫힘을 승하차 **후보**로 기록한다. 다시 열리지 않고 D로 출발하면 해당 지점의 탑승·하차를 확정한다. 대상 식별이 불명확하면 `확인 필요`로 남긴다.

step.5 차량 앱은 다음 지점으로 경로를 이어가고, 내비 예상 도착 시각이 기준보다 지연되면 해당 지점 보호자에게 지연을 알린다. 보호자의 `5분 늦어요`는 운전자에게 짧은 음성으로 전달한다.

step.6 모든 대상의 처리 상태를 확인하고 최종 목적지에 도착하면 운행을 종료한다. 완료된 보호자 링크는 더 이상 당일 운행 상태를 보여 주지 않는다.

## 2. 제품 개요

### 2.1 배경

학원 픽업과 반려견 유치원 픽드랍에서는 운전자가 여러 보호자에게 출발·접근·도착·승하차·지연을 반복 안내한다. 실제 반려견 유치원 기사와 견주의 문자 사례에서 도착 안내 누락, 순서 안내, 지연 설명, 답장 확인이 관찰됐다. 기존 안심 메시지는 이동 상태 공유 수요를 보여 주지만, 이 제품은 한 차량이 여러 지점을 순회하며 각 보호자에게 자기 대상의 상태를 전달하는 흐름을 다룬다.

### 2.2 목표·비목표

| 구분 | 내용 |
|---|---|
| 목표 | 운행 중 운전자 화면 입력 0회, 보호자별 적시 안내, 수동 연락 감소, 승하차 오판정 통제 |
| 1차 대상 | 반려견 유치원 기사·견주, 학원 픽업 운전자·보호자 |
| 1차 사업 가정 | 반려견 유치원 차량당 월 1만 원, 첫 1개월 무료 체험; 실제 도입 조건은 별도 검증 |
| 범위 밖 | 법적 주정차 가능 여부·과태료 판정, 차량 신호만으로 사람·반려견 신원 확정, 보호자 실시간 차량 위치의 무제한 공개 |
| 앱 카테고리 | **검토안: Mobility Services.** 서비스 카테고리·주행 중 허용 범위·매니페스트 설정은 Pleos 심사 기준으로 확인 필요 |

### 2.3 이번 버전과 후속 버전

| 단계 | 범위 | 상태 |
|---|---|---|
| 현재 시연 근거 | 기어·문·트렁크 이벤트, 내비 경유지 요청, 접근 지오펜스, TTS, 공조·무드등, 보호자 웹·중계 서버, 상태 머신 | 사용자 제공: 에뮬레이터 실행·테스트 24개 통과. 실차 검증 전 |

## 3. 용어와 데이터 모델

| 용어 | 정의·관리 주체 |
|---|---|
| 운행(Trip) | 한 번의 태우러가기 또는 데려다주기. 서버의 `trip_id`로 식별 |
| 지점(Stop) | 방문 순서, 장소, 대상, 보호자, 행위(태우기·내려주기)를 가진 단위. 서버 관리, 차량 앱에 복제 |
| 대상(Rider) | 아이 또는 반려견. 한 지점에 여러 대상이 있을 수 있음 |
| 보호자 링크 | 해당 운행·대상에 한정된 웹 접근 수단. 다른 대상·주소 조회 불가 |
| 접근 | 다음 지점 근처에 도달한 상태. `곧 도착` 안내 가능, 실제 도착 의미 아님 |
| 도착·대기 | 지점 인근에서 차량이 P로 정차한 상태. 실제 지점 일치 기준은 결정 필요 |
| 승하차 후보 | P 중 유효한 문 열림→닫힘 감지. 대상의 실제 탑승·인계를 보증하지 않음 |
| 확정 | 후보 뒤 문 재개방 없이 D로 출발하고, 대상 매핑에 모호성이 없는 상태 |
| 확인 필요 | 신호 누락, 다중 대상, 인계 미확인 등으로 자동 확정하지 못한 상태 |

## 4. 정보 구조와 화면 구성

### 4.1 차량 앱

| 화면 | 진입·표시 정보 | 행동·상태 분기 | 오류·빈값 |
|---|---|---|---|
| 운행 준비 | 모드, 대상·지점 순서, 방문 장소, 링크 연결 여부, 출발 버튼 | P이고 주행 제한이 허용할 때만 편집·시작. 출발 알림 수신자 범위 확인 | 대상·장소 누락 시 시작 비활성, 원인 표기 |
| 운행 중 요약 | 현재 상태, 다음 지점 이름, 예상 도착, 미처리 대상 수, 알림 결과 | 주행 중 조작 요구 없음. 상세 설정은 제한 상태 해제 시 표시 | 내비·네트워크 값 없음은 `정보 확인 중` 또는 `알림 전송 대기` |
| 도착·대기 | 현재 지점, 대기 경과 시간, 보호자 응답, 문 후보 상태 | P 중에만 `확인 필요` 처리 가능. 10분 대기 행동은 결정 필요 | 지점 밖 P는 도착으로 자동 판정하지 않음 |
| 확인 필요 | 대상·사유·확인 행동, 안전한 처리 시점 | 주행 중에는 배지만 표시. P이면서 주행 제한 해제 후 확인·수정 | 무응답이면 미확정 유지, 확정 알림 발송 금지 |
| 운행 종료 | 처리 완료·미확정 대상, 발송 실패 건, 종료 버튼 | 최종 목적지 도착만으로 자동 종료할지 결정 필요. 미확정 대상 있으면 종료 전 안내 | 네트워크 실패 시 로컬 기록을 보존하고 동기화 상태 표시 |

**화면 원칙**

- Pleos 화면은 Driving view와 앱 window로 구성된다. 앱은 Driving view·상태 표시줄·GNB를 그리거나 덮지 않는다. 목업의 지도는 내비 앱 영역인지 픽업 체크인 자체 화면인지 명확히 나눈다. 픽업 체크인은 별도의 상태 요약 화면으로 설계하고, 내비가 전면에 있어도 상태 처리와 TTS가 이어지도록 한다.
- Portrait에서는 `다음 지점·ETA·현재 상태`를 우선한다. Landscape에서는 현재 지점과 전체 순서를 함께 보여 줄 수 있다. 고정 픽셀 비율이 아닌 실제 앱 window 크기 변화에 대응한다.
- `CarUxRestrictions`를 기준으로 입력 가능 여부를 제어한다. P는 필요 조건일 수 있으나 P만으로 모든 입력을 허용하지 않는다. 주행 중 동영상·움직이는 이미지·장문 답장 표시를 제한한다.
- 이미지 흐름의 `응, 보내` 같은 운전자 음성 응답은 **현재 구현 확인된 TTS 범위에 포함되지 않는다.** 음성 입력이 필수이면 SpeechToText 연동·권한·오인식 대응을 별도 개발한다. 1차 권고는 자동 발송과 P 중 확인이다.
- TTS는 내비 안내와 오디오 포커스 충돌을 처리한다. 긴 문장과 반복 음성은 피한다.

### 4.2 보호자 모바일 웹

| 화면·영역 | 표시 | 행동·제한 |
|---|---|---|
| 운행 상태 | 내 대상의 출발, 순서, 접근, 도착·대기, 탑승·인계, 지연, 종료 상태와 시각 | 다른 대상의 이름·주소·상태는 숨김. 순서는 `앞에 1곳`처럼 숫자로만 표시 |
| 빠른 응답 | `5분 늦어요`, `받았어요`, 선택형 빠른 답장 | 대상·운행이 유효할 때만 허용. 반복 탭·중복 요청 방지 |
| 종료·만료 | `오늘 운행이 끝났어요` 또는 만료 안내 | 당일 운행 종료 후 상세 상태 접근 차단; 링크 만료 시점 결정 필요 |

## 5. 기능별 상세 정책

### 5.1 운행 준비·출발·경유지

**목표** 운행 대상과 수신자를 확정한 뒤 안전하게 출발하고, 내비 경로와 보호자 상태를 동기화한다.

| 항목 | 입력·기본값 | 필수 | 검증·처리 |
|---|---|---|---|
| 모드 | 태우러가기 / 데려다주기, 기본값 없음 | Y | 모드별 지점 행위와 문구 결정 |
| 지점 목록 | 순서·주소·대상·보호자 연결 | Y | 비활성 보호자·주소 없는 지점은 출발 전 안내 |
| 경로 | NaviHelper에 경유지 최대 2곳 요청, 이후 2곳씩 롤링 | Y | 요청 실패 시 재시도 및 운전자 안내. 경로 표시 성공과 운행 시작을 분리 기록 |
| 출발 | 운전자 시작 조작 후 D 전환 | Y | **권고:** 출발 알림은 한 운행에 한 번만. 현재 운행과 연결된 보호자에게만 발송 |
| 대상 수 | 수신자 수를 실제 데이터로 표시 | N | 목업의 `15명` 같은 고정 문구 금지 |

### 5.2 접근·도착·대기·순서

| 이벤트 | 선행 조건 | 처리 | 보호자 문구 예시 | 운전자 안내 |
|---|---|---|---|---|
| 접근 | 다음 지점 150m 등 접근 지오펜스 진입, 아직 접근 알림 없음 | 해당 지점 보호자에게 1회 | `3분 뒤 도착해요.` | 필요할 때만 `다음은 토리네입니다.` |
| 순서 변화 | 앞 지점 처리 완료 | 앞에 남은 지점 수 갱신 | `토리 앞에 1곳 남았어요.` | 원칙적으로 음성 없음 |
| 도착·대기 | 지점 인근 + P, 대상 지점 일치 | 해당 지점에 1회 도착 알림, 대기 타이머 시작 | `차가 정문 앞에 도착했어요.` | `도착했습니다.` 1회 |
| 대기 갱신 | P 유지, 3분 경과 | **권고:** 보호자에게 3분마다 무한 반복하지 않음. 최초 1회 + 의미 있는 상태 변화 시 갱신 | `차가 기다리고 있어요.` | 반복 음성 없음 |
| 장기 대기 | P 10분 유지 | 운전자에게 P 중 알림; 선택지가 주행 제한으로 불가하면 다음 허용 시점까지 보류 | 선택 시에만 추가 발송 | `10분째 기다리고 있어요.` |

접근 알림의 `3분 뒤`는 ETA가 유효할 때만 표시한다. 지오펜스만으로 정확한 3분을 보증하지 않는다. 도착은 지오펜스 진입만으로 선언하지 않는다.

### 5.3 탔어요·내렸어요

**배경** 문과 기어는 승하차 가능성을 보여 주지만 실제 사람·반려견 신원은 알 수 없다.

| 단계 | 조건·상태 | 처리 |
|---|---|---|
| 후보 생성 | 해당 지점 P + 허용 문 열림→닫힘 | 현재 지점에 후보 생성. 기본은 조수석·뒷문, 켄넬 플랜만 트렁크 포함 |
| 후보 무효 | 같은 문 재개방, 주행 중 문 이벤트, 운전석 문 | 해당 문 후보 취소 또는 무시 |
| 자동 확정 | 후보 유지 + D 출발 + 한 대상과 지점 매핑이 명확함 | **권고:** 출발 후 자동 발송. 운전자에게 발송 여부 질문 없음 |
| 인계 확인 | 데려다주기에서 보호자 `받았어요` 응답 | 응답을 인계 근거로 기록. 문 신호만 있는 경우 하차 확정과 보호자 인계 완료를 분리 |
| 확인 필요 | 문 신호 없음, 한 지점 여러 대상, 보호자 인계 확인 필요, 신호 충돌 | 주행 중 배지만 표시, 다음 P+제한 해제 때 한 번 질문. 미확정 상태로 보존 |
| 중복 방지 | 같은 지점·대상·행위 이벤트 재수신 | 동일 발송 키로 1회 처리 |

**중요:** 원고의 `문 사이클 수만큼 2명 확정`은 문 횟수만으로 누구인지 알 수 없어 안전하지 않다. 한 지점 여러 대상은 대상별 명시 확인 또는 별도 식별 근거가 생길 때까지 `확인 필요`가 권고안이다.

| 행위 | 보호자 문구 예시 | 운전자 TTS 예시 |
|---|---|
| 태우기 확정 | `지우가 탔어요.` | `지우가 탔어요. 다음은 하윤이네입니다.` |
| 내려주기 + 인계 확인 | `콩이를 보호자에게 인계했어요.` | `콩이 인계를 완료했어요.` |
| 내려주기 후보이나 인계 미확인 | `콩이의 하차를 확인 중이에요.` 또는 보호자 발송 보류 | `콩이 인계 확인이 필요해요.` — 다음 P에서만 처리 |

### 5.4 지연·보호자 응답

| 항목 | 기준·처리 | 중복·실패 |
|---|---|---|
| 지연 기준 | 다음 지점 출발 시 ETA와 현재 ETA 비교. `현재 ETA - 기준 ETA >= 5분`이면 해당 지점 보호자에게 알림 | ETA 값이 목업·결측이면 실서비스 자동 지연 판단하지 않음 |
| 재알림 | 직전 통지 지연값보다 `>= 3분` 더 늦어질 때만 재발송 | 같은 수준의 정체 변동은 무시 |
| 도착 직전 제한 | 원고의 `3분 전 알림 이후에는 보내지 않음`은 기준이 모호함. **권고:** ETA 3분 이하 또는 접근 알림 후에는 지연 재알림 중단 | 개발 전 확정 필요 |
| 보호자 `5분 늦어요` | 현재 지점의 보호자만 전송 가능. 운전자에게 한 문장 TTS | 같은 보호자의 반복 탭 제한; 자유 텍스트는 읽지 않음 |
| 확인성 답장 | `넵`, `천천히 오세요`는 차량 화면에만 간단히 표시 | TTS 없음 |

### 5.5 대기 중 공조·무드등

| 항목 | 처리 | 실패·제약 |
|---|---|---|
| 온도 | 차량이 지점 인근 P로 대기 중일 때 사전 설정 온도 요청 | 설정값·차량 지원 여부 확인. 요청 후 실제 상태 재조회 |
| 무드등 | 설정된 플랜·차량에서만 요청 | 미지원·실패 시 승하차·알림 흐름은 유지 |
| 안전 | 공조 제어 조건과 승객 유무, 차량 전원 상태 등 차량 정책 준수 | 실차 허용 범위 확인 전 일반 제공 기능으로 약속하지 않음 |

### 5.6 정차 주의 안내: 두 단계로 분리

| 단계 | 입력 | 출력 | 개발 상태 |
|---|---|---|---|
| A. P 대기 시간 | P 전환 시각, 지점별 설정 한도 | `정차한 지 3분이 지났어요. 주변 규정을 확인해 주세요.` | 원고 기준 설계 단계. 기존 기어 이벤트로 구현 예정 |
| B. 노면 표시 감지 | 황색 점선·실선·복선·백색 선의 실제 가용 데이터 | 감지 시 보조 주의 문구 | SDK·권한·가용성·정확도 미확인. 별도 탐색 과제 |

노면 표시만으로 정차 허용 여부·시간·단속 가능성을 판정하지 않는다. 법률·표지·시간대·지자체 규칙이 반영된 검증 자료가 확보되기 전에는 `5분 이내 허용` 같은 확정 문구를 제품에 쓰지 않는다. 황색 선 경고와 P 대기 시간 알림은 각각 독립적으로 켜고 끌 수 있게 설계한다.

## 6. 상태·시간·우선순위

| 상태 | 진입 조건 | 전환·종료 | 복원 기준 |
|---|---|---|---|
| 준비 | 운행 생성, 시작 전 | 시작 → 이동 중 | 서버 trip, 로컬 초안 |
| 이동 중 | 출발 D, 다음 지점 지정 | 접근 / 도착·대기 / 운행 종료 | 현재 지점·경유지 인덱스 |
| 접근 | 다음 지점 접근 지오펜스 | P+지점 일치 → 도착·대기; 지점 이탈은 이동 중 | 접근 알림 발송 여부 |
| 도착·대기 | 지점 인근 P | 문 이벤트 → 승하차 후보; D 이동 → 다음 지점 | P 시작 시각·지점 ID |
| 승하차 후보 | 유효 문 사이클 | 재개방 → 취소; D → 확정 또는 확인 필요 | 문 상태·후보 ID |
| 확인 필요 | 신호 모호·누락·인계 미확인 | P+허용 상태에서 확인 → 확정·취소 | 미해결 대상 목록 |
| 완료 | 마지막 지점·대상 처리 후 종료 | 링크 만료·기록 보관 | 서버 최종 상태 |

| 공통 규칙 | 처리 |
|---|---|
| 시각 | 서버 기록은 UTC 기준, 차량·보호자 UI는 현지 시각 표기. 기어·문 이벤트는 단조 시간 기준 순서 보존 |
| 이벤트 우선순위 | 명시적 운전자 확인 > 동일 지점의 유효 차량 신호 > 지오펜스 추정. 충돌 시 자동 확정 중단 |
| 중복 | `trip_id + stop_id + rider_id + event_type` 및 이벤트 버전으로 멱등 처리 |
| 재시작 | 포그라운드 서비스 재시작 후 서버·로컬 마지막 확정 이벤트를 재조합. 알림 발송 여부를 먼저 복원 |
| 네트워크 단절 | 상태는 로컬 큐에 보관, 보호자에게 `발송 완료`를 표시하지 않음. 재연결 후 유효 기간 안에서 순서대로 전송·중복 제거 |
| 운행 종료 | 미확정 대상·미전송 알림을 운전자에게 표시. 종료 허용 여부는 정책 결정 필요 |

## 7. 차량 SDK·플랫폼 연동

| 기능 | SDK/API·제공된 실측 | 개발 시 확인 | 미지원·값 없음 |
|---|---|---|---|
| 기어 | `Gear.registerGearSelection` 동작 확인 | 차량별 capability·권한·이벤트 지연 | 자동 승하차 확정 중단, 수동 확인 대기 |
| 문·트렁크 | `Door.registerDoorPosition` 뒷문·트렁크 열림→닫힘 확인 | 도어별 구분, capability | 후보 생성 불가, 수동 확인 |
| 착좌·벨트 | `Seat.registerSeatOccupancy`, `registerSeatBeltBuckledState` 값 불안정 | 실차 가용성 | 1차 판정에 사용하지 않음 |

| ETA·정체 | `getWaypointInfo().remainTime`, `onDrivingInfo`, `RouteStateInfo.trafficStatus`, `requestTrip` 수신 확인·값 목업 | 실차 값·갱신 주기 | 지연 자동 알림 비활성, 시간 미표시 |
| 접근 | `FusedLocation.addProximityAlert` 1.2km / 150m 동작 확인 | `isSupported`, 정확도·오탐 | 도착 자동 판정 금지, 내비 도착 정보 보조 |

Pleos 공식 문서는 Vehicle SDK와 FusedLocation이 차량별로 달라질 수 있으며 `checkXXXCapabilities`, `isSupported`로 가용성을 확인하도록 안내한다. 실제 운행 제공 범위는 에뮬레이터 성공과 분리해 실차 검증한다.

## 8. 데이터·서버·보호자 웹 연계

| 데이터 | 원본·관리 주체 | 전송·권한 | 삭제·보관 |
|---|---|---|---|
| 운행·지점·대상·보호자 연결 | 중계 서버/운영 주체 | 차량 앱은 현재 운행만 읽기; 보호자는 자기 대상만 조회 | 보관 기간 결정 필요 |
| 차량 신호 | 차량 앱/SDK | 서버에는 필요한 상태 이벤트·시각만 전송, 원시 센서 로그 최소화 | 장기 원본 저장 금지 권고 |
| 위치·ETA | 차량 SDK·내비, 차량 앱 | 차량 위치는 접근·ETA 계산에 사용. 보호자에게 상세 좌표 공개 여부 결정 필요 | 위치 처리·보관·법적 요건 검토 |
| 보호자 응답 | 보호자 웹 | 해당 trip·stop·rider에 한정 | 운행 종료 뒤 접근 차단, 기록 보관 기간 결정 필요 |
| 발송 결과 | 중계 서버 | queued/sent/delivered/failed 등 구분 | 장애 조사 범위로 보관, 기간 결정 필요 |

**권한·보안 정책**

- 보호자 웹에는 다른 가정의 이름·주소·경유지 상세를 표시하지 않는다. 링크는 추측하기 어려운 토큰으로 발급하고 해당 운행·대상에만 묶는다.
- `아이·반려견 위치를 수집하지 않는다`는 원고의 뜻은 **대상 개인의 별도 위치를 수집하지 않는다**로 정리한다. 차량 위치와 경유지는 처리하므로 `위치를 전혀 수집하지 않는다`고 표현하지 않는다.
- 공유 차량에서 운전자 교체·계정 전환 시 이전 운행의 이름·링크·토큰을 노출하지 않는다. 토큰은 안전한 저장소에 보관한다.
- 공모전 동의서(03)는 참가자 정보 처리에 대한 동의이며, 실제 보호자·아동·차량 위치 처리의 동의·고지를 대신하지 않는다. 별도 정책·법률 검토가 필요하다.

## 9. 알림·문구 정책

| 대상 | 트리거 | 문구 예시 | 발송 제한 |
|---|---|---|---|
| 현재 운행 보호자 | 운행 시작 | `토리의 픽업 운행을 시작했어요.` | 운행당 1회; 대상별 내용만 |
| 다음 지점 보호자 | 접근, 유효 ETA | `약 3분 뒤 도착해요.` | 지점당 1회 |
| 다음 지점 보호자 | 지점 인근 P | `차가 도착해 기다리고 있어요.` | 지점당 1회 |
| 해당 보호자 | 태우기 확정 | `토리가 탔어요.` | 대상·행위당 1회 |
| 해당 보호자 | 내려주기·인계 확인 | `콩이를 인계했어요.` | 대상·행위당 1회 |
| 다음 지점 보호자 | 지연 >= 5분 | `정체로 약 8분 늦어요.` | 증가분 >= 3분 때 재발송; 접근 후 재발송 제한 |
| 운전자 | 보호자 `5분 늦어요` | `토리 보호자가 5분 늦는다고 알렸어요.` | 1회 TTS, 중복 탭 무시 |
| 운전자 | 승하차 확인 필요 | `확인이 필요한 탑승이 있어요.` | 주행 중 조작 요청 금지, 다음 P에서 상세 |
| 운전자 | P 대기 3분 | `정차한 지 3분이 지났어요. 주변 규정을 확인해 주세요.` | 지점당 1회; 후속 기능 |

모든 알림은 `생성됨`, `서버 전송됨`, `보호자 전달됨`, `실패`를 구분한다. 서버 전송 성공만으로 보호자가 읽었다고 말하지 않는다. `넵` 같은 확인성 답장은 TTS로 읽지 않는다.

## 10. 핵심 시나리오·예외

### 10.1 학원 태우러가기

1. 운전자가 P 상태에서 지우·하윤의 픽업 순서와 보호자를 확인하고 운행을 시작한다.
2. D 출발 후 이번 운행 보호자에게 출발 상태를 보낸다.
3. 지우 지점 150m 접근 시 지우 보호자에게 `곧 도착`, 지점 인근 P 시 `도착`을 보낸다.
4. 지우 지점 P에서 뒷문 열림→닫힘이 발생하고, 재개방 없이 D로 출발하면 지우의 탑승을 확정한다. 지우 보호자에게 `지우가 탔어요`를 보낸다.
5. 다음 지점 하윤 보호자에게는 하윤 관련 순서·접근·도착만 보낸다. 지우 탑승 정보가 하윤 보호자에게 전송되는 원고의 표현은 수신 대상 오류로 수정한다.
6. 문 신호가 없거나 대상이 모호하면 `확인 필요`로 보류하고, 다음 P 및 주행 제한 해제 시점에 한 번 확인한다.

### 10.2 반려견 유치원 하원(데려다주기)

1. 기사가 유치원에서 `데려다주기`를 시작하고 콩이 집을 포함한 경로를 요청한다.
2. 콩이 보호자에게 출발·접근·지연 상태를 알린다. 이 시나리오의 `콩이네 픽업 도착`은 **`콩이네 하차 지점 도착`**으로 표기한다.
3. 집 인근 P에서 문·트렁크 신호를 하차 후보로 기록한다. `받았어요` 응답이 있으면 인계 완료를 기록한다.
4. 보호자의 `넵`, `천천히 오세요`는 운전자 화면에만 간단히 표시한다. `5분 늦어요` 같은 행동에 영향을 주는 응답만 짧게 읽는다.

### 10.3 장애·오판정

| 상황 | 기대 동작 |
|---|---|
| 트렁크에 가방만 적재 | 기본 플랜은 후보 생성 안 함. 켄넬 플랜도 대상 매핑 불명확하면 확인 필요 |
| 문을 닫았다 다시 열기 | 이전 후보 취소. 새 닫힘 이후 다시 평가 |
| 한 지점 2명·2마리 | 문 사이클 수로 신원 확정하지 않음. 대상별 확인 필요 |
| P가 아닌 상태의 문 이벤트 | 승하차 판정에 사용하지 않음 |
| 접근 지오펜스 오탐 | 접근 1회 이후 지점 이탈·재진입 중복 발송 금지; 도착은 P와 지점 일치 필요 |
| 네트워크 단절 | 로컬 기록·전송 대기. 운전자에게 `전송 대기` 표시. 복구 시 멱등 재시도 |
| 보호자 링크 만료·오발송 | 링크 접근 차단·새 링크 발급, 발송 취소·정정 절차 필요 |
| 앱 재시작 | 운행 상태·발송 키 복원, 이미 보낸 알림 재발송 금지 |

## 11. 측정 지표·검증 기준

| 지표 | 정의·목표 성격 |
|---|---|
| 기사 4주 유지율 | 첫 운행 주에서 4주 뒤에도 픽업 체크인으로 운행한 기사 비율. 목표치는 실증 후 확정 |
| 보호자 월간 활성률 | 링크를 받은 보호자 중 해당 월 1회 이상 상태를 확인한 고유 보호자 비율 |
| MAU | 한 달에 차량 앱으로 운행한 기사 + 모바일 웹에서 상태를 1회 이상 확인한 고유 보호자. 중복 계정 제거 기준 필요 |
| 자동 알림 성공률 | 자동 발송 대상 이벤트 중 전달 완료로 확인된 비율. 전송 성공과 전달 성공 분리 |
| 수동 연락 감소율 | 실증 전후 기사 1운행당 수동 전화·문자 횟수 비교 |
| 무료→유료 전환율 | 무료 체험 종료 업체 중 유료 계약 업체 비율 |

시장 규모는 사용자 제공 조사 기준 `영업 중이며 상호에 유치원이 포함된 412곳`이다. 이는 상호 기준 자체 집계이고 공식 유치원 총수가 아니다. 초기 5곳 도입 가정에서 기사 5명·보호자 30~80명으로 **예상 MAU 35~85명**이며, 10곳이면 70~170명이다. 보호자 10~20명/업체, 월간 링크 이용률 60~80% 가정에 기반한다. 실사용·Pleos 탑재 차량 여부를 확인해 갱신한다. [공공데이터 원자료](https://www.data.go.kr/data/15107029/fileData.do).
